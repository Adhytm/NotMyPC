## 🎯 为什么需要这个工具？

在全国高校的宿舍网、校园 Wi-Fi 或城中村租房宽带中，几乎每一位同学都经历过这些折磨：
- **经典困境 1**：打游戏每隔几分钟跳一次几百毫秒的 Ping，看直播中途频繁缓冲，但一打开 Speedtest 测速，下行带宽居然跑满了？！
- **经典困境 2**：向学校网络中心报修，网管上门看了一眼：“别人都没反映卡，就你卡，是不是你电脑中病毒了 / 离 AP 太远 / 开了后台下载？”
- **经典困境 3**：网络抖动具有瞬时性与突发性，等运维慢悠悠登录交换机查看时，网络“暂时恢复正常”，投诉直接被当成“无故障关闭”。

### 核心设计哲学：全维度交叉验证，形成完整证据链

单一 ICMP Ping 容易受到防火墙 Rate-limit（限速）误判，普通测速软件只测瞬时下行带宽。本工具的核心是**多维度交叉对照 + 故障瞬间保全现场**：

```
                              ┌── [1] 本地默认网关 (验证宿舍内 AP/交换机链路)
                              │
  [本机内核收发计数器] ──────┼── [2] 公共 DNS: 阿里/腾讯 (验证校内汇聚/出口链路)
                              │
                              ├── [3] 真实 HTTP 应用层连接 (验证防火墙/代理/TCP 握手)
                              │
                              ├── [4] 持续流媒体分块下载 (模拟真实直播，捕获传输停顿)
                              │
                              └── [5] Wi-Fi 信号/漫游/省电模式 (排除设备自身无线假死)
```

1. **操作系统内核计数器**：直接读取操作系统内核网卡硬件收发包差值，不受 ICMP 限速影响，最权威。
2. **内外网低频交叉对照**：若本地网关延迟 < 2ms 且 0 丢包，但出口 DNS 延迟暴涨或超时，即可直接证明“故障在校园网出口链路，与学生宿舍端无关”。
3. **真实流媒体切片下载**：模拟直播视频流，若分块读取时间超过 1 秒即判定为“停顿”，精准揪出“连接正常但传输卡死”的伪通畅。
4. **故障自动秒级快照**：一旦发生异常，瞬时冻结当前 Wi-Fi 信号、BSSID、IP 配置、路由表、ARP 表与错误流水，形成不可篡改的日志证据。
5. **分级路由自动追踪**：连续超时自动对【网关】、【公共 DNS】、【外网视频站】发起 Traceroute，精确指出卡死在第几跳路由器。

## 📦 双模运行：根据需求任选其一

### 现代 Web 实时仪表盘架构 (v6.0)
- **技术栈**：TypeScript + Hono 独立高性能后端引擎 + Next.js 15 (React 19) 前端仪表盘 + SSE 实时推送 + Recharts 趋势图。
- **核心特点**：跨平台适配（Windows / macOS / Linux）、全量网络异常快照抽屉、分层路由追踪拓扑、多目标延迟折线图、一键导出 CSV/JSON 报表。
- **历史归档**：项目原型最早为单文件 Python 脚本（v1.0 ~ v5.2），现已全部升级为前后端解耦的现代系统。早期原型与历史演进记录已沉淀至本地 `archive/`。

## 🚀 快速上手

#### Windows 用户（一键双击）：
直接双击根目录下的 **`start-gui.bat`** 即可，脚本会自动检测 Node.js 环境并安装依赖拉起服务，随后在浏览器打开 [http://localhost:3002](http://localhost:3002)。

#### 命令行运行（全平台通用）：
```bash
# 1. 安装依赖
npm install

# 2. 启动开发模式（同时拉起引擎 3001 端口与前端 3002 端口）
npm run dev

# 3. 生产模式构建与启动（可选）
npm run build
npm start
```
启动成功后，浏览器访问：**`http://localhost:3002`**。

## 📋 输出证据链清单 (自动保存于 `logs/` 目录)

| 证据文件名 | 记录内容 | 维权证据效力 |
| :--- | :--- | :--- |
| **`timeline_log.txt`** | 秒级异常时间轴（记录每次丢包、高延迟、中断起止时长） | 运维可直接拿时间戳对照机房核心交换机 Syslog 日志 |
| **`snapshot_log.txt`** | 异常瞬间抓取的全量网络现场（Wi-Fi/IP/路由/ARP/TCP） | 保全现场，防止运维事后以“现场没复现”为由结单 |
| **`trace_log.txt`** | 故障触发时的跨跳路由追踪（网关、DNS、外网目标） | 精确定位故障是宿管间 AP、汇聚交换机还是出口防火墙 |
| **`wifi_log.txt`** | Wi-Fi 信号强度、协商速率、信道、AP 漫游历史 CSV | 铁证证明不是你离 AP 远，也不是因为信号衰减导致的断流 |
| **`download_log.txt`** | 持续分块下载速度、TTFB（首字节延迟）、传输停顿记录 | 证明实际业务（看视频、打游戏、看直播）受到严重中断 |
| **`raw_ping_log.txt`** | 产生异常时底层的 Ping 原始标准输出文本 | 原始第一手证据，防质疑数据真实性 |
| **`monitor_export.csv`**| 包含 P95/P99 尾部延迟、抖动（Jitter）、丢包率等结构化数据 | 可直接导入 Excel 绘制汇报图表提交至校长信箱或工信部 |

## 🥊 维权对线指南：如何利用本数据向网管提交工单？

1. **如果网管说：“你是不是离路由器太远，Wi-Fi 信号差？”**
   - 拿出 `wifi_log.txt` 与异常快照中的无线信息：
   - *“老师您看，故障发生时我的 Wi-Fi 信号强度稳定在 90% 以上，协商速率 866Mbps，并且全程没有发生 AP 漫游，证明物理无线链路完全健康。”*

2. **如果网管说：“别人都不卡就你卡，是你电脑网卡坏了或者中了木马。”**
   - 拿出 `ping_log.txt` 与 `snapshot_log.txt`：
   - *“您看交叉对比数据，在我丢包的同一秒内，我对本机默认网关的 Ping 延迟只有 1.2ms 且 0 丢包，内核网卡收发计数器正常递增；但阿里 DNS、腾讯 DNS 与 B站 HTTP 连接全部超时，这完全是校内汇聚向上出口丢包的特征。”*

3. **如果网管说：“测速跑满了 100M，网没问题啊。”**
   - 拿出 `timeline_log.txt` 和 `download_log.txt`：
   - *“测速只代表空闲时的峰值吞吐量。这里有持续 2 小时的下载切片日志，平均每隔 3 分钟就会出现单块超过 1.5 秒的完全停顿，P99 尾部延迟高达 850ms，且伴随中断事件，这已经严重影响教学和正常业务。”*

4. **如果网管说：“不是我们学校的问题，是外网运营商线路挂了。”**
   - 拿出 `trace_log.txt`：
   - *“这是连续超时触发的路由追踪，在第 2 跳（宿舍楼汇聚交换机 10.x.x.x）就已经 100% 丢包未响应，根本没有到达运营商公共网段。”*

## ⚙️ 探测参数与高级配置

在 TypeScript 版本中，修改 `packages/engine/src/config.ts`；在 Python 版本中，直接修改 `ping.py` 顶部的配置区：

| 参数名 | 默认值 | 作用说明 |
| :--- | :--- | :--- |
| `PING_INTERVAL` | `2` 秒 | Ping 探测周期，保守频率，严防被校园网防火墙判为攻击限速 |
| `SPIKE_THRESHOLD_MS` | `100` ms | 延迟超过该阈值即记录高延迟 Spike 告警 |
| `DOWNLOAD_INTERVAL` | `60` 秒 | 持续下载测速的探测间隔 |
| `DOWNLOAD_STALL_THRESHOLD`| `1.0` 秒 | 下载单块读取耗时超此数值视作一次流媒体停顿 |
| `CONSECUTIVE_FAIL_FOR_TRACERT`| `3` 次 | 连续所有目标超时达到此次数才执行 Tracert，避免误触发耗时追踪 |
| `SNAPSHOT_COOLDOWN` | `30` 秒 | 异常快照冷却时间，防止短时间内高频异常将磁盘刷满 |
